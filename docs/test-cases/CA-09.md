# Test cases - CA-09: Citirea automată a documentului (OCR) pe server

User Story: Ca utilizator, vreau ca aplicația să citească singură datele de pe bon, ca să nu le tastez.

Abordare de dezvoltare: tradițională.

## Pregătire pentru verificarea manuală

1. Microserviciul OCR pornit (llama.cpp cu Qwen3-VL 4B, pe `http://127.0.0.1:8080`):
   ```powershell
   & 'C:\Users\Cris\llama\bin\llama-server.exe' -m 'C:\Users\Cris\llama\models\Qwen3VL-4B-Instruct-Q4_K_M.gguf' --mmproj 'C:\Users\Cris\llama\models\mmproj-Qwen3VL-4B-Instruct-F16.gguf' -ngl 99 -c 16384 -np 1 --host 127.0.0.1 --port 8080
   ```
   Modelul (fișierele `.gguf`) se descarcă de pe huggingface.co/Qwen/Qwen3-VL-4B-Instruct-GGUF; llama.cpp de pe github.com/ggml-org/llama.cpp (build Windows Vulkan). Adresa se schimbă cu `OCR_URL` în `server/.env`.
2. Migrarea aplicată: `cd server` și `npm run db:migrate` (tabelele `file` și `ocr_result`).
3. Serverul pornit: `cd server` și `npm run dev`. Pozele încărcate se păstrează în `server/uploads/` (nu intră în git).
4. Aplicația pornită: `cd mobile` și `npx expo start`, deschisă pe un telefon în Expo Go, cu un cont confirmat.

## Rularea testelor automate

Din rădăcina repository-ului (testele nu au nevoie de microserviciul OCR: răspunsurile lui sunt simulate):

```bash
npm test
npm run test:coverage
```

## Rezultate

Verificare manuală pe un bon real Carrefour Express (15.11.2026): toate valorile citite corect (magazin, data 12.11.2026, ora 17:58, total 26,17, card, 4 produse și reducerea de -3,20), în aproximativ 31 de secunde.

Poză reală de pe telefon (Mega Image, 1326x2048, ținut în mână, cu reclame tipărite peste bon; 15.11.2026): toate sumele corecte, inclusiv 2 produse la kilogram și reducerea „15% REDUCERE” de -4,90, produsele se adună la totalul 107,01; mici greșeli în nume („MEGA IMAGES”, „F I ACTOZA”) și absorbantele încadrate la „Alimente”. Durata: 117 secunde. Prima încercare a eșuat pentru că două citiri simultane au depășit memoria (contextul) llama.cpp: acum citirile se fac pe rând, iar llama.cpp pornește cu `-c 16384 -np 1`.

Factură generată (21.11.2026, 3 linii, TVA 21% și 11%, fără coloană „total cu TVA” pe linie): tipul, furnizorul, data facturii, totalul de plată 424,18, plata prin transfer, prețurile unitare fără TVA și TVA-ul fiecărei linii citite corect. La prima încercare modelul a pus valoarea fără TVA drept total al liniei; serverul o corectează acum automat. Durata: 41–63 de secunde.

Facturi reale PDF (21.11.2026): Invoice_1 (1 pagină, VANESSE SARL, 184,20 RON, 21 s), Invoice_2 (2 pagini, furnizor din Grecia, sume în RON și EUR, totalul 103,30 RON pe pagina 2, ~77 s), Invoice_3 (eMAG / Dante International, 26,53 RON, ~39 s): toate valorile corecte, liniile se adună exact la total. Salvarea Invoice_1 ca „Factură scanată”, cu prețul unitar fără TVA și TVA-ul liniei, verificată prin API.

Viteză (24.11.2026): modelul scrie acum un răspuns compact (valori simple, fără „confidence” la fiecare valoare; siguranța o stabilește serverul din verificări), iar telefonul trimite poze de cel mult 1536 px. Pe aceleași documente, toate citite corect: bonul lung Mega Image de pe telefon ~45 s (înainte 92–121 s), bonul Carrefour ~30 s, Invoice_1 12–21 s, Invoice_2 (2 pagini) ~28 s (înainte ~77 s), Invoice_3 ~11 s. Poza se trimite ÎNAINTEA instrucțiunilor: invers, modelul a citit greșit cifre pe poza de telefon.
